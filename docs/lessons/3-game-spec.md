# The founding spec (#3) · 28 Sep 2026

- **Numbers:** the session's estimate was $25 for the runbook and the spec together; $30 when this PR opened and about $45 by the merge, past the estimate but under twice it. The spec PR opened at 19:06 UTC, 64 minutes after the runbook PR, with issue #2 for the owner's choices; the owner answered every choice by 20:07 through two pages built for it (the choices with defaults, and the same garden drawn in four art styles), and the spec was approved and merged the same evening. The overage is the design work the brief didn't ask for: the owner joined the session, the architecture was reworked (`docs/lessons/1-runbook.md`), and the spec grew from a six-level ladder to an eight-level one with a systems map, the climate loop, politics and a living map.
- **Went well:** designing in the conversation before writing (the systems map, then the ladder level by level, each confirmed by the owner) meant the spec was written once. The graph check caught three full paths in the spec to files that don't exist yet; naming future files without their folder, as the decision records do, was enough.
- **Lessons:**
  - A founding spec for a systems game is a different document from a feature spec: the model and the systems map come before the first slice, and the template's one-page rule doesn't apply. → The spec template says the founding spec is the one exception; later specs point at its systems map instead of restating it (`docs/specs/TEMPLATE.md`).
  - When the owner is present, a design conversation is cheaper than a design document: three rounds of chat settled the stack, the systems and the ladder in under an hour, where a written proposal would have taken a round trip each. Worth remembering for the first slice's parts: ask the owner while they're here.
  - A `needs-owner` issue with defaults got no answer for an hour; a page with the same choices as pre-selected options, saving to a store the session reads back, got all ten in a few minutes, and a page that drew the four art styles got the pick in one. → For a choice the owner has to make, build the page that shows the options rather than the issue that lists them, and keep the issue as the record (the `feature` playbook, the needs-owner queue).
